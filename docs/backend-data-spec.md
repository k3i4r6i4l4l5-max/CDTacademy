# Динамические данные и требования к бэкенду CDTacademy

Дата анализа: 3 ноября 2026 года.

Документ предназначен для передачи бэкенд-разработчику. Он описывает данные текущего приложения, действующие правила, API и предлагаемый порядок переноса в полноценную базу данных.

Обозначения:

- **Реализовано** — поведение существует в коде приложения.
- **Предлагается** — расширение для следующего этапа; его пока нет в действующем API.

## 1. Текущее состояние

Приложение использует Nuxt 4, Vue 3, TypeScript и Tailwind CSS 4. Серверные обработчики работают на Nitro. Редактор кода построен на CodeMirror 6.

Базовый бэкенд уже существует: API с префиксом `/api/platform`, авторизация через cookie, проверка прав и файловое хранилище `.data/platform.json`. Путь хранилища можно изменить через `PLATFORM_DATA_FILE`.

| Категория | Где находится сейчас | Что передать новому бэкенду |
|---|---|---|
| Пользователи, группы, сессии | Серверный JSON-файл | Хранение, авторизацию и права |
| Тесты и вопросы | Серверный JSON-файл | Хранение, публикацию и версионирование |
| Конспекты | Серверный JSON-файл | Хранение и публикацию |
| Попытки и оценки | Серверный JSON-файл | Приём ответов, проверку, историю и выборки |
| Общая аналитика | Рассчитывается сервером | Агрегации по данным БД |
| Фильтры результатов | Выполняются в браузере | Серверную фильтрацию и пагинацию |
| Встроенный курс JavaScript | TypeScript-файлы приложения | Перенос в БД при необходимости редактирования курса |
| Прогресс встроенного курса | localStorage | Персональное серверное хранение |
| Черновики ответов теста | localStorage | Серверное автосохранение при необходимости |

Файловая схема рассчитана на один процесс. При переносе на несколько процессов запись должна выполняться через БД с транзакциями.

## 2. Пользователи

**Реализовано.** Публичная модель пользователя: `PublicUser`.

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | Генерируется сервером, уникально |
| `login` | string | Непустой, до 80 символов после обработки входных данных |
| `role` | enum | `student`, `teacher`, `admin` |
| `groupId` | string или null | Ссылка на существующую группу; для студента |
| `password` | string, только сервер | Сейчас содержит соль и scrypt-хеш; в новой схеме рекомендуется имя `passwordHash` |

Правила:

1. Логин обрезается по краям; уникальность и поиск при входе проверяются без учёта регистра.
2. Пароль чувствителен к регистру. Текущие ограничения: 3–200 символов. Минимум 3 оставлен для совместимости с демо-аккаунтами.
3. Публичная регистрация разрешена только с `role: "student"`.
4. Администратор может создавать аккаунты всех трёх ролей.
5. Изменение существующей роли допускается между `student` и `teacher`. Текущий API не позволяет через эту операцию назначить роль администратора или понизить существующего администратора.
6. Хеш пароля не возвращается клиенту. Пароль из формы используется только при входе или создании аккаунта.
7. Роль определяется сервером по записи пользователя при каждом запросе. Выбор роли в форме входа не выдаёт права.

**Предлагается:** добавить `createdAt`, `updatedAt`, статус аккаунта и управляемый администратором сброс пароля. Эти поля и операции сейчас отсутствуют.

## 3. Сессии

**Реализовано.**

| Поле | Тип | Назначение |
|---|---|---|
| `token` | string | SHA-256-хеш случайного токена; предлагается имя `tokenHash` в БД |
| `userId` | string | Пользователь сессии |
| `expires` | number | Момент истечения в миллисекундах Unix; в БД можно хранить как `expiresAt` |

Сырой токен передаётся в cookie `practice_session`: HttpOnly, SameSite=Lax, Path=/, срок действия 7 дней. Secure включается для HTTPS. При выходе запись сессии и cookie удаляются. Истёкшие сессии не дают доступ.

Переименование полей при переносе требует адаптера или согласованного изменения серверного кода; публичные ответы API менять для этого необязательно.

## 4. Группы

**Реализовано.**

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | Уникальный идентификатор |
| `name` | string | Отображаемое название |

Начальные группы: `is-11` → «ИС-11», `is-12` → «ИС-12», `pi-11` → «ПИ-11».

Студент может выбрать свою группу при регистрации или в профиле. Преподаватель и администратор могут изменить группу студента. `null` означает «Без группы».

Группа сейчас используется для распределения и аналитики. Она не ограничивает доступ к материалам: опубликованные тесты и конспекты доступны всем студентам.

**Предлагается:** CRUD групп. При добавлении удаления нужно определить, запрещать ли удаление используемой группы или переводить студентов в «Без группы».

## 5. Конспекты

**Реализовано.** Модель: `NoteDefinition`.

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | Генерируется сервером |
| `title` | string | Непустой заголовок, до 200 символов |
| `body` | string | Непустой текст, до 100 000 символов |
| `published` | boolean | Доступен ли студентам |
| `updatedAt` | string | Серверная дата изменения в ISO 8601 |

Преподаватели и администраторы создают и редактируют материалы, включая публикацию и снятие с публикации. Студенты получают только опубликованные конспекты.

Импорт `.md`/`.txt` читает содержимое файла на фронтенде и отправляет текст. Форма ограничивает файл размером 150 000 байт. Сам файл и его имя сейчас не сохраняются. Загрузка файлов в объектное хранилище для сохранения текущего поведения не нужна.

Отображаются обычный текст и блоки кода в тройных обратных кавычках. Полноценный Markdown-парсер не подключён; HTML из текста не исполняется.

**Предлагается:** автор `createdBy`, дата создания и история редакций. При добавлении общего доступа персонала эти поля нужны для учёта изменений, а не для автоматического ограничения видимости.

## 6. Тесты

**Реализовано.** Модель: `TestDefinition`.

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | Генерируется сервером |
| `title` | string | Непустое название, до 200 символов |
| `notes` | string | Собственный текст конспекта, до 100 000 символов |
| `noteId` | string или null | Необязательная ссылка на библиотечный конспект |
| `passPercent` | number | Порог прохождения от 0 до 100 включительно |
| `published` | boolean | Статус публикации |
| `questions` | Question[] | От 1 до 100 вопросов, порядок значим |
| `updatedAt` | string | Серверная дата изменения |
| `version` | string | Вычисляемая сервером версия выдаваемого содержимого |

Если указан `noteId`, при выдаче используется актуальный текст связанного конспекта. Собственное поле `notes` не является второй независимо отображаемой частью.

Публикация теста с неопубликованным связанным конспектом отклоняется. Если конспект снят с публикации позднее, студенту не выдаётся его текст, а версия связанного теста меняется. Сам тест при этом автоматически не снимается с публикации.

Без связанного конспекта версия равна `updatedAt` теста. Со связанным конспектом она рассчитывается из даты изменения теста, даты изменения конспекта и его статуса публикации. При переносе допустим другой непрозрачный идентификатор версии, если сохраняется это поведение.

## 7. Вопросы и типы ответов

**Реализовано.** Модель: `Question`.

| Поле | Тип | Правило |
|---|---|---|
| `id` | string | Уникально внутри теста; сохраняется при редактировании того же вопроса |
| `prompt` | string | Непустое условие, до 5 000 символов |
| `type` | enum | Один из пяти типов ниже |
| `options` | string[] | Только для выбора ответа; для остальных типов пустой массив |
| `expected` | string | Эталон для автоматических типов; для ручных пустая строка |
| `points` | integer | Максимальные баллы, от 1 до 100 |

| Тип | Поле в интерфейсе | Способ проверки |
|---|---|---|
| `text` | Короткое текстовое поле | Сравнение с эталоном после удаления пробелов по краям; регистр учитывается |
| `choice` | Выбор одного варианта | Сравнение выбранной строки с эталоном |
| `free` | Многострочный текст | Ручная оценка преподавателем или администратором |
| `code` | Редактор JavaScript | Ручная оценка преподавателем или администратором |
| `code_reference` | Редактор JavaScript | Текстовое сравнение с эталоном |

Дополнительные ограничения:

- Для `choice`: 2–20 уникальных непустых вариантов, каждый до 500 символов; эталон должен входить в варианты.
- Для `text`: непустой эталон до 5 000 символов.
- Для `code_reference`: непустой эталон до 30 000 символов; CRLF/CR нормализуются в LF, пробелы по краям удаляются. Все остальные символы должны совпадать.
- `code_reference` не запускает код и не проверяет эквивалентность алгоритмов.
- При нормализации вопросов в отдельную таблицу нужен `position`, поскольку сейчас порядок задаётся массивом.

## 8. Попытки прохождения

**Реализовано.** Модель: `Submission`.

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | Серверный идентификатор попытки |
| `testId` | string | Исходный тест |
| `testTitle` | string | Снимок названия теста |
| `studentId` | string | Авторизованный студент, определяется сервером |
| `studentLogin` | string | Снимок логина |
| `submittedAt` | string | Серверная дата отправки |
| `passPercent` | number | Снимок порога прохождения |
| `answers` | SubmittedAnswer[] | Ответы со снимками вопросов |

Правила приёма:

1. Отправлять ответы может только студент.
2. Тест должен существовать и быть опубликован.
3. Клиент передаёт версию теста; устаревшая версия отклоняется с `409`.
4. Ответ обязателен на каждый вопрос: непустая строка до 30 000 символов.
5. Для выбора ответ должен входить в сохранённые варианты.
6. Клиент не назначает себе баллы и не выбирает `studentId`.
7. После отправки студент не редактирует попытку. Повторное прохождение создаёт новую попытку; текущего ограничения на их число нет.

## 9. Ответы, снимки и ручная оценка

**Реализовано.** Модель: `SubmittedAnswer`.

| Поле | Тип | Назначение |
|---|---|---|
| `question` | Question | Полная копия вопроса на момент отправки |
| `value` | string | Текст ответа, выбранная строка или исходный код |
| `points` | number или null | Полученные баллы; null означает ожидание проверки |
| `comment` | string | Комментарий проверяющего, до 5 000 символов |

Снимок включает условие, тип, варианты, эталон и максимум баллов. Изменения исходного теста не должны менять старые попытки. В нормализованной БД недостаточно хранить только ссылку на текущий вопрос.

Автоматические типы получают либо 0, либо полный максимум вопроса. Для `free` и `code` при отправке устанавливается `points: null`. Персонал может выставить конечное число баллов от 0 до максимума включительно, в том числе дробное, и комментарий. Текущий интерфейс предлагает шаг 0,5; API не ограничивает оценку только этим шагом.

**Предлагается:** сохранять `reviewedBy`, `reviewedAt` и историю повторных оценок. Этих данных сейчас нет.

### Расчёт результата

```text
max = сумма максимумов всех вопросов
earned = сумма выставленных баллов; null временно считается как 0
pending = есть хотя бы один ответ с points = null
percent = earned / max * 100, отображение округлено до 2 знаков
passed = !pending && max > 0 && earned * 100 >= passPercent * max
```

Проверка порога выполняется без округления. До завершения ручной проверки процент предварительный, а попытка не считается пройденной.

### Выдача эталонов

При загрузке теста студенту `expected` заменяется пустой строкой. Сейчас API попыток возвращает владельцу полный снимок ответа, включая `question.expected`. Поэтому текущая реализация раскрывает эталоны уже отправленной попытки.

**Предлагается перед переносом согласовать политику:** показывать эталоны после отправки, после окончательной проверки или не показывать студентам. Если раскрытие не требуется, нужен отдельный DTO студенческой попытки, исключающий эталон, при сохранении полного снимка на сервере.

## 10. Аналитика и выборки

**Реализовано:** общая аналитика рассчитывается на сервере и доступна только администратору.

| Показатель | Определение |
|---|---|
| `students` | Текущее число пользователей с ролью student |
| `teachers` | Текущее число пользователей с ролью teacher |
| `tests` | Число всех тестов, включая неопубликованные |
| `attempts` | Количество отправленных попыток |
| `pending` | Количество попыток с неоценёнными ответами |
| `passed` | Количество успешных попыток |
| `passedStudents` | Количество уникальных студентов с успешной попыткой |
| `average` | Средний процент по полностью проверенным попыткам; 0, если таких нет |
| `byTest` | Те же показатели попыток отдельно по каждому тесту |
| `byGroup` | Те же показатели по текущей группе студента, включая «Без группы» |

Один студент может иметь несколько успешных попыток. Поэтому `passed` и `passedStudents` — разные показатели. Средний результат учитывает все проверенные попытки, а не только лучшую или последнюю.

Сейчас преподаватель получает все попытки и фильтрует их в браузере: по тесту, студенту, максимальному проценту и статусу. Преподавателю также доступны счётчики успешных попыток и уникальных прошедших студентов, но не общий endpoint аналитики.

**Предлагается** серверная выборка:

```http
GET /api/platform/submissions?testId=...&studentId=...&maxPercent=60&status=pending&page=1&pageSize=20
```

Это новый контракт, пока не реализованный. `maxPercent=60` означает «60% или меньше», включая предварительные результаты, как в текущем фильтре. Статусы: `pending`, `passed`, `failed`; отсутствие статуса — все. Для сохранения текущего поведения процент фильтруется после округления до двух знаков; изменить это правило можно только согласованно с интерфейсом.

Предлагаемый ответ: `{ items, total, page, pageSize }`. Сортировка должна быть стабильной, например `submittedAt DESC, id DESC`. Студент всегда получает только свои попытки независимо от переданных фильтров. Переход с текущего массива на такой объект требует обновления фронтенда.

## 11. Встроенный курс JavaScript

**Реализовано как статические данные**, отдельно от преподавательских тестов. Основные модели находятся в `shared/types/course.ts`, содержимое — в `app/data/course.ts` и `app/data/taskExamples.ts`.

| Сущность | Существующие данные |
|---|---|
| Урок | `id`, `title`, `description`, `minutes`, массив `theory`, итоговый `task` |
| Теория | `title`, `text`, `example`, небольшая практика `practice` |
| Практика | `id`, `prompt`, `answer`, `hint`, необязательные `starter`, `expected` |
| Итоговая задача | `title`, `prompt`, `functionName`, `starter`, `cases`, `hint`, необязательный `example` |
| Проверочный случай | `args: unknown[]`, `expected: unknown` |
| Пример похожей реализации | `title`, `description`, `code`, `steps`, `transfer` |

Сейчас порядок определяется массивами. При переносе необходимы идентификатор курса, связи между его частями и явный порядок уроков, теории и проверочных случаев. Теоретическим блокам и итоговым задачам стоит назначить стабильные ID.

**Предлагается:** отдельные операции управления курсом, статус публикации и версия материалов. Их нет в текущем редакторе тестов.

Код самостоятельного курса выполняется в браузерном Web Worker с ограничением времени 2 секунды. Это отличается от ручной проверки `code` и текстового сравнения `code_reference` в тестах. Если результаты курса станут основанием официальной оценки, проверку нужно выполнять доверенным серверным механизмом. Переданный клиентом `passed: true` не должен подтверждать такое прохождение. Серверный запуск произвольного кода — отдельный модуль, сейчас отсутствующий.

## 12. Прогресс курса и черновики

### Прогресс курса

**Реализовано локально:** ключ `practice:javascript:v2` в localStorage.

- `selected` — выбранный урок.
- `answers` — словарь по ключу задания.
- Каждый ответ: `value`, `passed`, `feedback`.
- Ключ небольшой практики: `<lessonId>:<practiceId>`; итоговой задачи: `<lessonId>:code`.
- Завершённость урока и счётчики вычисляются из ответов.

Сейчас этот ключ общий для браузера и не разделён по аккаунтам.

**Предлагается** хранить на сервере: `userId`, `courseId`, `lessonId`, `exerciseId`, `contentVersion`, `value`, результат проверки, обратную связь и `updatedAt`. Выбранный урок можно хранить отдельно для пары пользователь/курс. Прогресс должен принадлежать конкретному пользователю.

### Черновики тестов

**Реализовано локально:** ключ `practice:test:<userId>:<testId>`, значение `{ version, answers }`. Ответы представлены словарём `questionId → string`. После успешной отправки черновик удаляется.

**Предлагается:** серверное автосохранение с полями `userId`, `testId`, `version`, `answers`, `updatedAt`, а также контроль конфликтов при редактировании с нескольких устройств. Черновик не является отправленной попыткой и не участвует в статистике.

При обновлении теста текущий интерфейс переносит ответы только для вопросов с прежними ID, типом и условием. Новая версия не должна молча затирать введённые ответы.

| Отправлять попытки | Да | Нет | Нет |
| Читать свои попытки | Да | Все попытки | Все попытки |
| Оценивать произвольный текст и код | Нет | Да | Да |
| Получать список студентов | Нет | Да | Да |
| Менять группу | Только свою | Студентам | Студентам |
| Получать полный список пользователей | Нет | Нет | Да |
| Создавать аккаунты через панель | Нет | Нет | Да |
| Назначать и снимать роль преподавателя | Нет | Нет | Да |

Публично доступны регистрация студента, вход, список групп и проверка текущей сессии. Сейчас нет ограничения материалов или результатов по автору-преподавателю: персонал работает с общим набором. Ограничение «только мои группы/тесты» потребует новой модели назначений и отдельных правил.

## 14. Действующее API

Префикс всех путей: `/api/platform`. Это текущие маршруты, которые можно сохранить при замене файлового хранилища на БД.

| Метод | Путь | Вход / назначение |
|---|---|---|
| GET | `/me` | Ответ `{ user: PublicUser или null }` |
| GET | `/groups` | Массив групп |
| POST | `/register` | `{ login, password, role: "student", groupId? }`; создаёт сессию |
| POST | `/login` | `{ login, password, role }`; создаёт сессию |
| POST | `/logout` | Завершает текущую сессию |
| PATCH | `/me/group` | `{ groupId }`; собственная группа студента |
| GET | `/users` | Все публичные пользователи; только администратор |
| POST | `/users` | `{ login, password, role, groupId? }`; только администратор |
| PATCH | `/users/:id/role` | `{ role: "student" или "teacher" }` |
| GET | `/students` | Массив студентов; персоналу |
| PATCH | `/students/:id/group` | `{ groupId }`; персоналу |
| GET | `/notes` | Массив доступных конспектов |
| POST | `/notes` | `{ title, body, published }` |
| PUT | `/notes/:id` | Полное обновление конспекта |
| GET | `/tests` | Массив доступных тестов |
| POST | `/tests` | `{ title, notes, noteId?, passPercent, published, questions }` |
| PUT | `/tests/:id` | Полное обновление теста |
| GET | `/submissions` | Свои попытки студенту, все попытки персоналу |
| POST | `/submissions` | `{ testId, version, answers: Record<string, string> }` |
| PATCH | `/submissions/:id` | `{ grades: [{ questionId, points, comment }] }` |
| GET | `/analytics` | Общие показатели и разрезы; только администратор |

Для преподавательского предпросмотра `/tests?audience=student` и `/notes?audience=student` используют студенческую фильтрацию публикации и содержимого. Параметр не даёт студенту дополнительных прав.

Удаление материалов, CRUD групп, смена пароля, управление курсом, серверный прогресс и серверные черновики пока не имеют API.

### Пример отправки ответов

```json
{
  "testId": "arrays-basics",
  "version": "opaque-server-version",
  "answers": {
    "q1": "0",
    "q2": "Новую длину",
    "q3": "map создаёт массив результатов, forEach выполняет действие для элементов.",
    "q4": "function triple(values) { return values.map(value => value * 3); }"
  }
}
```

### Ошибки

| HTTP | Пример причины |
|---|---|
| 400 | Некорректные поля, неизвестная группа, недопустимые баллы |
| 401 | Нет действующей сессии или неверные данные входа |
| 403 | Не хватает прав, выбрана чужая роль при входе, запрещённая роль регистрации |
| 404 | Тест, конспект, пользователь или попытка не найдены |
| 409 | Логин занят либо версия теста устарела |
| 413 | Превышено ограничение размера запроса |

Текущий обработчик ограничивает заявленный Content-Length значением 1 000 000 байт и отклоняет изменяющие запросы с чужим Origin. При выделении отдельного API нужно согласовать домены, cookie и передачу credentials, сохранив проверки доступа. Фронтенд использует HTTP-статусы для обработки конфликтов.

## 15. Предлагаемая структура БД

Это вариант модели для переноса, а не описание уже подключённой БД.

| Таблица | Основные данные и связи |
|---|---|
| `users` | Пользователь, хеш пароля, роль, group_id |
| `sessions` | Хеш токена, user_id, срок действия |
| `groups` | Учебные группы |
| `notes` | Содержимое, публикация, даты |
| `tests` | Настройки, встроенный конспект, note_id, версия |
| `test_questions` | test_id, порядок, условие, тип, варианты, эталон, максимум |
| `submissions` | test_id, student_id, дата, снимки названия и порога |
| `submission_answers` | submission_id, снимок вопроса, ответ, оценка и комментарий |
| `courses`, `lessons`, `theory_blocks`, `exercises` | Второй этап: управляемый курс и его содержимое |
| `course_progress` | Второй этап: персональные ответы и результаты заданий |
| `test_drafts` | Второй этап: неотправленные ответы |

Варианты выбора, проверочные случаи и снимки вопросов допустимо хранить в JSON-полях. Эталоны остаются серверными данными с отдельными правилами выдачи.

Ограничения и индексы:

- Уникальность нормализованного логина и хеша сессии.
- Связи пользователя с группой, сессий с пользователем, вопросов с тестом, ответов с попыткой.
- Уникальность `(test_id, question_id)`; индексы порядка вопросов.
- Индексы попыток по `(student_id, submitted_at)` и `(test_id, submitted_at)`.
- Проверки допустимых ролей, типов вопросов, диапазонов порога и баллов.
- Транзакция на создание попытки со всеми ответами и на пакетную ручную оценку.
- Проверка версии и статуса публикации должна быть согласована с записью попытки, чтобы параллельное редактирование не обошло контроль версии.
- История попыток сохраняется при последующих изменениях материала. Политику удаления исходных тестов и пользователей нужно определить до добавления удаления.

## 16. Синхронизация интерфейса

Сейчас открытые видимые страницы обновляют данные каждые 5 секунд, при возвращении фокуса и при событии `platform:changed`. Данные преподавателя и студента читаются из общего хранилища. Редактируемые формы отделены от обновляемых списков.

При замене бэкенда нужно сохранить:

1. Появление опубликованных материалов у студента и скрытие снятых с публикации.
2. Обновление связанного конспекта и версии теста.
3. Получение новых баллов и комментариев без ручной перезагрузки страницы.
4. Актуальность группы и прав пользователя.
5. Сохранность введённых ответов при фоновых обновлениях.

Polling можно оставить на первом этапе. WebSocket или SSE — возможное последующее расширение; сейчас они не используются.

## 17. Данные, которые остаются на фронтенде

- Активная вкладка панели и раскрытые блоки.
- Положение курсора, выделение и прокрутка редактора кода.
- Состояние показа пароля.
- Индикаторы загрузки и ошибки текущей формы.
- Несохранённые изменения формы до отправки, если отдельно не вводится автосохранение.
- Выбранные фильтры как состояние интерфейса; значения используются в запросе серверной выборки.

Счётчики прогресса и проценты — вычисляемые данные. Их можно возвращать из API, но не следует принимать от клиента как достоверные оценки.

## 18. Порядок переноса и приёмка

### Этап 1. Замена файлового хранилища

1. Создать схему БД и миграции.
2. Перенести пользователей, группы, материалы, попытки и снимки ответов, сохранив ID и связи.
3. Сохранить совместимость с существующими scrypt-хешами либо реализовать их проверку на переходный период. Повторно хешировать готовый хеш как пароль нельзя.
4. Сессии либо перенести с сохранением срока, либо согласованно завершить с повторным входом пользователей.
5. Сохранить текущие контракты API и права ролей.
6. Добавить серверные фильтры и пагинацию с согласованным обновлением фронтенда.

### Этап 2. Персональные данные обучения

1. Добавить серверный прогресс курса с привязкой к пользователю.
2. Добавить серверные черновики и правила конфликтов между устройствами.
3. Не присваивать общий локальный прогресс автоматически случайному вошедшему аккаунту: старые данные не содержат владельца. Перенос должен быть явным; результат проверки при необходимости подтверждается повторно.

### Этап 3. Управляемый курс и расширения

Добавить редактирование курса через панель, управление группами, учёт авторов и проверяющих. Серверное исполнение кода вводить отдельной задачей, если оно требуется для доверенной оценки.

### Критерии приёмки

- Регистрация не позволяет получить роль преподавателя или администратора.
- Студент не получает чужие попытки, черновики материалов и административную аналитику.
- Права проверяются сервером и меняются после изменения роли в записи пользователя.
- Преподаватель и студент видят одинаковое опубликованное содержимое при предпросмотре.
- Устаревшая версия теста отклоняется с 409 без потери введённого черновика.
- Все автоматические баллы рассчитываются сервером; ручные оценки ограничены максимумом вопроса.
- Пока есть неоценённый ответ, попытка не считается пройденной.
- Старые попытки не меняются после редактирования теста.
- Фильтр «60% или меньше» включает пограничное значение 60%.
- Количество успешных попыток отличается от числа уникальных прошедших студентов.
- Групповая аналитика использует текущую группу, как в действующем приложении.
- Данные сохраняются после перезапуска; параллельные записи не теряют изменения.
- После второго этапа прогресс разделён по пользователям и доступен на другом устройстве.
