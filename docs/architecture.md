# Архитектура приложения

Приложение состоит из интерфейса Nuxt/Vue, серверных обработчиков Nitro и общих TypeScript-типов. Основные команды, требования и демо-аккаунты приведены в [README](../README.md).

## Ответственность частей

| Путь | За что отвечает |
|---|---|
| `app/pages/` | Маршруты, загрузка данных и сборка интерфейса страниц |
| `app/components/` | Редактор кода, библиотека, управление участниками и другие блоки UI |
| `app/composables/useAuth.ts` | Текущий пользователь, обновление сессии, выход |
| `app/composables/usePlatformSync.ts` | Периодическое обновление данных открытой страницы |
| `app/composables/useLearning.ts` | Локальный прогресс самостоятельного курса |
| `app/middleware/account.global.ts` | Переход ко входу при отсутствии сессии, защита страниц панели |
| `server/api/platform/[...path].ts` | Проверка данных и прав, API пользователей, материалов и результатов |
| `server/utils/platformStore.ts` | Чтение/запись файла, начальные аккаунты, хеши паролей и токенов |
| `shared/types/` | Контракты данных, общие для клиента и сервера |
| `shared/utils/platform.ts` | Расчёт результата попытки, подписи ролей |

Клиент отправляет запрос в `/api/platform/...`. Сервер читает сессию из cookie, определяет пользователя и проверяет права. Для изменений сервер валидирует данные и сохраняет обновлённое хранилище. Клиент получает только результат операции и данные, доступные его роли.

Проверка маршрутов в браузере нужна для навигации. Реальное ограничение доступа находится в API: скрытая кнопка не заменяет серверную проверку роли.

## Авторизация и пользователи

`useAuth` использует Nuxt `useState`, поэтому меню, страницы и middleware работают с общим состоянием текущего пользователя. При SSR запрос сессии передаёт cookie исходного запроса через `useRequestFetch`.

Вход проверяет логин, пароль и выбранную роль. Пароль хранится как результат scrypt с индивидуальной солью. При входе сервер выдаёт случайный токен в HttpOnly cookie; в файле сохраняется хеш токена. Сессия действует 7 дней и удаляется при выходе. При каждой защищённой операции роль читается из текущей записи пользователя, поэтому изменение роли не требует новой выдачи токена.

Регистрация допускает только `student`. Администратор может создать аккаунт любой из трёх ролей и изменить существующую роль между студентом и преподавателем. Через изменение роли нельзя понизить администратора. Только администратор имеет доступ к общей аналитике.

Учебные группы используются для профиля, распределения студентов и аналитики. Сейчас они не ограничивают доступ к опубликованным материалам: опубликованные тесты и конспекты доступны всем студентам.

## Основные маршруты API

Все маршруты ниже имеют префикс `/api/platform`.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /me` | Текущая сессия или `null` | Все |
| `GET /groups` | Список групп | Все |
| `POST /login` | Вход с проверкой роли | Все |
| `POST /register` | Регистрация студента | Все; только роль `student` |
| `POST /logout` | Завершение сессии | Вошедший пользователь |
| `GET /tests` | Тесты; студенту — только опубликованные, без эталонов | Вошедший пользователь |
| `POST /tests`, `PUT /tests/:id` | Создание и редактирование теста | Преподаватель, администратор |
| `GET /notes` | Конспекты; студенту — только опубликованные | Вошедший пользователь |
| `POST /notes`, `PUT /notes/:id` | Создание и редактирование конспекта | Преподаватель, администратор |
| `GET /submissions` | Свои попытки студента или все попытки для персонала | Вошедший пользователь |
| `POST /submissions` | Отправка ответов по актуальной версии теста | Студент |
| `PATCH /submissions/:id` | Ручная оценка текста и кода | Преподаватель, администратор |
| `GET /students` | Список студентов | Преподаватель, администратор |
| `PATCH /students/:id/group` | Изменение группы студента | Преподаватель, администратор |
| `PATCH /me/group` | Изменение своей группы | Студент |
| `GET /users`, `POST /users` | Список пользователей, создание аккаунта | Администратор |
| `PATCH /users/:id/role` | Назначение/снятие роли преподавателя | Администратор |
| `GET /analytics` | Общая статистика, разрезы по тестам и группам | Администратор |

Для предпросмотра преподаватель получает `/tests?audience=student` и `/notes?audience=student`: фильтрация публикации и скрытие эталонов соответствуют студенческому представлению.

## Материалы и версии

Тест хранит вопросы, типы ответов, эталоны, баллы, порог, собственный текст конспекта и необязательный `noteId`. При наличии `noteId` сервер подставляет актуальный текст связанного конспекта. Непубликованный конспект не передаётся студенту. Публикация теста с неопубликованным связанным конспектом отклоняется.

`version` в ответе API учитывает редактирование теста и связанного конспекта. При отправке студент передаёт версию, по которой отвечал. Если она устарела, API возвращает `409`. Страница предлагает открыть актуальную версию, сохранив ответы на вопросы с прежними ID, формулировкой и типом.

Текст конспекта отображается через `TestNotes`: обычный текст и блоки кода между тройными обратными кавычками. Компонент не использует HTML-вставку. Импорт `.md`/`.txt` читает текст файла; полноценный Markdown-парсер не подключён.

## Ответы и оценка

Сервер сам рассчитывает автоматические баллы, используя сохранённые эталоны. Переданные клиентом баллы не принимаются. Обычный код и произвольный текст ожидают ручной оценки; преподаватель задаёт баллы в пределах максимума вопроса и комментарий.

Попытка сохраняет снимок вопросов, эталонов, максимальных баллов, названия теста и проходного порога. Последующие изменения теста не меняют эту попытку.

`resultOf` используется и интерфейсом, и аналитикой. Пока есть неоценённые ответы, результат предварительный и попытка не считается пройденной. Условия прохождения сравниваются без округления; округляется только отображаемый процент. Успешные попытки и уникальные студенты считаются раздельно. Группировка аналитики использует текущую группу пользователя.

«Код по эталону» сравнивает текст, не поведение программы. Самостоятельный курс `/learn` работает иначе: `checkCode` выполняет функцию в Web Worker и сравнивает результаты тестовых случаев. Время выполнения ограничено двумя секундами; worker завершается после ответа или тайм-аута. Это отделяет выполнение от потока интерфейса, но не является защищённой системой экзаменов.

## Синхронизация

Видимые страницы опрашивают API каждые 5 секунд и при возврате фокуса. При уходе со страницы обработчики и таймер удаляются. Запросы обновляют загруженные списки; редактируемые формы хранят отдельные черновики и не заменяются результатом опроса.

Главная студента получает опубликованные материалы через `StudentMaterials`. Конспекты, тесты, результаты, профиль группы и аналитика читают одни серверные данные. Черновики материалов доступны только персоналу.

## Хранилище и эксплуатация

Данные хранятся в `.data/platform.json` или по пути `PLATFORM_DATA_FILE`. При отсутствии файла создаются стартовые аккаунты, группы и демонстрационный тест. При чтении существующего файла добавляются недостающие поля групп и библиотеки конспектов; пользователи и результаты сохраняются.

Запись выполняется во временный соседний файл с последующим переименованием. Обработчики читают данные после асинхронного разбора тела запроса; изменения и запись выполняются синхронно. Эта схема рассчитана на один процесс. Для нескольких серверных процессов нужна база данных с транзакциями.

Файл содержит данные пользователей и сессии, поэтому исключён из Git. Для переноса сохраните его вместе с постоянным путём и рабочим каталогом запуска. Самостоятельная программа и неотправленные черновики дополнительно используют localStorage браузера.

## Проверки

`test/platform.cjs` проверяет самостоятельный курс на статической сборке. `test/admin.cjs` создаёт временное хранилище, запускает отдельный Node-сервер и проверяет API и интерфейс. Он покрывает регистрацию, права, публикацию, ручные оценки, фильтры, группы и изменения, получаемые студентом без перезагрузки. Запросы браузера перенаправляются к тестовому серверу, чтобы проверки не зависели от локальных настроек прокси Chrome.
